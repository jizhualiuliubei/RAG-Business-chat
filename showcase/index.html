RAG 链路：六个阶段做准确率工程

制度类问答的准确率不来自模型参数，而是拆在解析、切片、改写、召回、重排与生成六个环节里。 每一段都写清两件事：不这么做会坏在哪，以及实际怎么做的。

架构选型：为什么是 Agentic Workflow

制度问答既要结果可控，又要能处理需要工具判断的问题。这两件事指向两个极端，而工程上的答案是把它们分层组合。

全部交给 Workflow

把检索、过滤、生成每一步都写死在代码里，确定性最高。但流程只能穷举已知情况， 遇到需要临时查时间、读档案、调外部系统的请求就无能为力。

适用：流程完全固定的批处理与定时任务。

全部交给 Agent

让模型自主决定每一步做什么。灵活度高，但行为难以复现：同一份制度、同一个问题， 两次回答引用的条款可能不一样，而制度问答必须可追溯。

适用：目标开放、路径不固定的探索型任务。

本系统的做法：Agentic Workflow

用确定性流程守住骨架，在需要工具判断的位置嵌入 Agent。 主链路走固定的六阶段，保证引用来源可复现；需要组合工具的场景单独开一条 Agent 路径， 由模型自主选择检索、取当前时间或读取用户档案。

代码上分成两层：Workflow 层是 qa_service.stream_answer 里的六阶段编排； Agent 层是 rag_agent.py 中用 create_agent 挂载三个工具得到的决策节点。 两条路径复用同一套混合检索，所以检索质量保持一致。

记忆设计：短期、长期与实体三层

对话历史是证据，结构化状态才是结论。本系统按信息类型选择存储介质，结构化字段走关系库精确查， 非结构化知识走向量库做语义检索。

短期记忆对话上下文
落库在 message 表，取用时先做滑动窗口 + 摘要压缩： 历史超过 HISTORY_SUMMARY_TRIGGER_MESSAGES（默认 6）条时，把更早的对话交给模型压成一段摘要， 只保留最近 HISTORY_SUMMARY_KEEP_MESSAGES（默认 2）条原文。 这样追问「那这个流程需要谁审批」这类省略主语的问题时，模型仍然知道上文。
长期记忆企业知识资产
制度文档经解析、切片、向量化后写入 Zilliz / Milvus，按 chunk 粒度存储，每个切片带 enterprise_id、kb_id、doc_id、source、chunk_id 元数据。 问答时用问题做语义检索，把命中的证据注入上下文。检索始终带企业与知识库过滤，不同租户的数据不会互相命中。
实体记忆结构化抽取
用户主动提供的信息（姓名、称呼、身份、偏好）经 ToolStrategy 与 Pydantic Schema 抽成结构化字段写入 user_profile，每轮注入。写入前用触发词预筛，只对像自我陈述的消息调用模型， 控制额外开销。

上下文工程：装配顺序决定回答质量

Prompt 按固定顺序分区装配：顶部注入当前日期时间解决模型不知道「现在」的问题； 随后是用户档案，无记录时显式写明「无记录」，压缩模型编造用户信息的空间； 再接会话附件与已知信息，证据带 [n] 编号与出处； 最后是用户问题。

两份来源分区注入，不混在一起。会话附件只属于当前账号当前会话，与知识库冲突时要求并列说明差异，不合并成确定结论。 高优先级规则（用户身份只以档案为准）写在最前，不会被后续内容覆盖。
