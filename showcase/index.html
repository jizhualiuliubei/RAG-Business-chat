RAG 链路：六个阶段做准确率工程

制度类问答的准确率不只取决于模型参数 —— 采样温度、提示词都会影响输出；但真正决定上限的是 证据取得准不准。所以这条链路被拆成解析、切片、改写、召回、重排与生成六段。

架构选型：为什么是 Agentic Workflow

制度问答既要结果可控，又要能处理需要工具判断的问题。这两件事指向两个极端，而工程上的答案是把它们分层组合。

本系统的做法：Agentic Workflow

用 Workflow 固定住流程骨架保证可控，在需要灵活判断的节点嵌入 Agent —— 两者不是二选一， 而是分层组合。

Workflow 骨架：从准备到落库的一条固定流程。 用户提问后先准备：取该企业的模型 Key、取当前企业的有效文档白名单、提取用户档案、 把更早的历史压成摘要、检索当前会话的附件。 接着进入检索阶段：查询改写（口语翻成制度语体，一问多求再拆分）→ 一次性批量向量化 → 向量召回与 BM25 全库召回 → 两路归一化融合（条款号、文档名等硬信号在这一步加分） → cross-encoder 精排 → 阈值过滤。 最后是生成与落库：命中知识库就按引用溯源回答、没命中就说明知识库未覆盖； 回答流式推送并附上引用来源，问答与来源一并落库。 这几段的顺序由业务决定、不随问题变化，所以写死成流程 —— 每次提问都走同一条路，引用来源才可复现。

Agent 用在两处。 一是记忆提取：每轮从用户消息里抽出姓名、称呼、偏好这类结构化信息，由模型判断该不该调用工具写进档案； 二是工具化问答：另开一条路径，挂上「知识库检索」「当前时间」「用户档案」三个工具， 由模型自主决定调哪个，再通过 MCP 通道把计算器这类通用能力放到独立进程里。 两条路径复用同一套检索，检索质量与主链路一致。

边界划在这里：制度问答要求引用可追溯，让模型自主决定检索步骤会让来源变得不可预测， 所以这段固定不动；而涉及时间、档案、外部工具时确实需要模型自己判断， 这部分灵活性收在少数节点里。

记忆设计：短期、长期与实体三层

对话历史是证据，结构化状态才是结论。本系统按信息类型选择存储介质，结构化字段走关系库精确查， 非结构化知识走向量库做语义检索。

短期记忆对话上下文
一轮问答落库成一条用户消息加一条助手消息。取用时做全量历史 + 摘要压缩： 历史超过 6 条时，把更早的对话交给模型压成一段摘要，只保留最近 2 条原文一起注入。 这样追问「那这个流程需要谁审批」这类省略主语的问题时，模型仍然知道上文。
长期记忆企业知识资产
制度文档经解析、切片、向量化后写入向量库，按切片粒度存储，每片都带企业与知识库标识。 问答时用问题做语义检索，把命中的证据注入上下文；检索始终带企业过滤，不同租户的数据不会互相命中。
实体记忆结构化抽取
用户主动提供的信息 —— 姓名、称呼、身份、偏好 —— 由模型抽成结构化字段写入档案，每轮注入。 写入前先用触发词预筛，只对像自我陈述的消息调用模型，控制额外开销。

上下文工程：装配顺序决定回答质量

每次模型调用能看到的上下文，按固定顺序装配，越靠前优先级越高：

  1. 系统指令身份、边界与硬规则（用户身份只以档案为准、无依据必须拒答、文档冲突并列引用），写在最前，不被后续内容覆盖
  2. 更早对话摘要只在更早的历史被压缩过时才出现
  3. 最近 2 轮对话原文保留语气与细节
  4. 会话附件仅当前会话上传过附件、且有片段命中时才注入
  5. 用户档案结构化实体记忆；没有记录时显式写「无记录」，压缩编造空间
  6. 当前日期时间模型不知道「现在」，日期与星期类问题靠它
  7. 已知信息检索到的知识库证据，每条带 [n] 编号与出处（文件名 · 知识库）
  8. 用户问题放在最后，紧邻要回答的任务

两条来源分区注入：会话附件与知识库证据各成一块，冲突时要求并列说明差异，不合并成确定结论。 附件只属于当前账号当前会话，换个会话就看不到；知识库证据始终按企业与知识库过滤， 不同租户之间互不可见。
