RAG 机制说明

系统围绕企业制度问答做准确率工程。企业问题经常包含条款号、金额、时间、审批角色和跨文档条件，所以 RAG 不只依赖向量相似度，而是把结构化解析、硬关键词召回、Rerank 和引用约束串成完整链路。

入库阶段

  • DOCX 按标题、段落、条款号提取。
  • PDF 优先读取文本层，扫描 PDF 使用 OCR。
  • CSV / XLSX / XLS 保留 Sheet、表头、行号和值。
  • 默认切片参数：CHUNK_SIZE=350、CHUNK_OVERLAP=80。
  • chunk 写入文档名、章节、条款号、页码、企业、知识库和文档元数据。

检索与生成阶段

  • 查询改写识别条款号、文档名、章节名和业务关键词。
  • 混合检索组合向量、BM25、条款精确召回和元数据过滤。
  • Rerank 把真正回答问题的证据排到前面。
  • 跨文档问题通过多证据补召回补齐主证据和辅助证据。
  • 生成时要求引用编号；证据不足时明确拒答。

Agent 机制说明

项目中的 Agent 相关能力主要体现在工具调用、MCP 扩展和记忆提取。首页默认问答链路保持可控 RAG，Agent 能力用于需要工具选择、用户档案、时间信息或扩展外部能力的场景。

@tool 本地工具

  • 知识库检索工具：按当前企业和知识库范围检索。
  • 当前时间工具：回答时间相关问题。
  • 用户档案工具：读取长期用户档案注入上下文。

MCP 工具扩展

  • 通过 MCP server 加载计算器、日期时间等工具。
  • 工具能力与模型推理分离，便于后续接企业内部系统。
  • 避免把所有业务能力都写进 Prompt。

记忆机制

  • 最近历史窗口：HISTORY_ROUNDS=10。
  • LangGraph InMemorySaver 按 conversation_id 保存会话状态。
  • 摘要压缩中间件控制长对话上下文长度。
  • ToolStrategy 提取姓名、身份、偏好写入 user_profile。

数据库设计

数据库围绕企业隔离和账号隔离设计。enterprise_id 是企业级边界，user_id 是个人会话、消息和附件边界。系统平台资产也作为 system 企业处理，模型 Key 从后台加密保存。

表用途关键字段与约束
enterprise企业主体企业名称、企业代码、状态、联系人、审核信息；状态包含 pending_review / active / rejected / disabled / deleted。
enterprise_model_key企业模型配置DeepSeek / SiliconFlow Key 加密保存，只展示遮罩状态和后四位。
users用户账号角色 system_admin / enterprise_admin / employee；用户名企业内唯一。
knowledge_base / document知识库和文档知识库企业内唯一；文档保存解析状态、失败原因、切片数和更新时间。
conversation / message会话和消息按 enterprise_id + user_id 隔离，管理员和员工不会互相看到最近会话。
conversation_attachment / conversation_attachment_chunk会话附件临时 RAG附件只属于当前企业、当前账号、当前会话；删除会话时清理附件切片。
evaluation_dataset / evaluation_run / evaluation_case_result评测中心题集、任务、逐题结果和报告按企业隔离。
audit_logs操作审计记录审核、代管、删除、Key 更新等关键治理动作，不保存敏感明文。
