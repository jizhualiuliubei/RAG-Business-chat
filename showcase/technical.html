技术说明

三个决定回答质量的技术选择

这套系统的重点不在"接了哪个大模型"，而在文档怎么入库、证据怎么召回、 Agent 能力边界怎么划、多企业数据怎么隔离。下面按 RAG 链路、Agent 与记忆、数据库与权限三部分说明。

一、RAG 检索与生成链路

企业制度问题经常包含条款号、金额、时间、审批角色和跨文档条件。所以检索不能只依赖向量相似度， 而是把结构化解析、硬关键词召回、重排和引用约束串成一条完整链路。

入库阶段
环节做法
文档解析DOCX 按标题、段落、条款号抽取；PDF 优先读文本层，无文本层时走 OCR；CSV / XLSX / XLS 保留 Sheet、表头、行号和值。
结构化切片默认 CHUNK_SIZE=350、CHUNK_OVERLAP=80。每个 chunk 写入文档名、章节、条款号、页码 / Sheet、enterprise_id、kb_id、doc_id、chunk_id。
向量入库BGE-M3 生成 embedding，写入 Zilliz / Milvus 统一 collection，靠元数据过滤实现企业与知识库隔离。
失败可见解析失败写入 failure_reason，在文档管理中直接暴露原因，例如缺 OCR 依赖、文件损坏或向量写入失败。
检索与生成阶段
环节做法
查询改写用 DeepSeek 做轻量改写：识别条款号、文档名、章节名，补齐金额、角色与流程关键词。只改检索词，不改用户原问题。
混合检索向量检索处理语义相近问法，BM25 处理编号与硬关键词，条款号精确召回处理 HR-01-001 这类短编号，元数据过滤保证不跨企业检索。
融合重排候选结果融合去重后经 Rerank 排序；跨文档问题补召回主证据与辅助证据，避免只命中一份制度导致要点缺失。
约束生成要求按引用编号作答；证据不足时明确拒答。正式知识库来源与会话附件来源分区注入，冲突时并列说明差异。

二、Agent 工具与记忆机制

项目同时提供"手动 RAG"和"Agent RAG"两条路径。制度问答、引用要求强、评测任务优先走手动 RAG， 保证可控与可复盘；需要时间、档案、外部工具或多步组合的问题才使用 Agent RAG。

工

本地 @tool 工具

把知识库检索、当前时间、用户档案封装为 Agent 可调用工具。工具只返回当前企业授权范围内的数据； 调用失败时返回明确错误，而不是让模型继续编造工具结果。

M

MCP 工具扩展

通过独立 MCP server 加载计算器、日期时间等外部能力，工具能力与模型推理分离， 避免把所有业务能力都塞进 Prompt，也便于后续接企业内部系统。

记

记忆是组合方案，不是单一方案

最近 N 轮历史窗口（HISTORY_ROUNDS=10）控制上下文长度与成本；LangGraph InMemorySaver 按 thread_id = conversation_id 隔离会话内记忆； SummarizationMiddleware 在消息超阈值后摘要历史，保留最近 2 条原文。

档

长期用户档案

用户主动提供的姓名、称呼、身份、偏好，经 ToolStrategy + Pydantic Schema 结构化提取后 写入 user_profile 表。只回答已经落库的稳定信息，不从历史对话里猜测身份。

三、数据库与权限设计

数据库围绕多租户设计：enterprise_id 是企业级隔离边界，user_id 是会话、消息与附件的隔离边界。 系统平台资产本身也是一个企业资产，企业代码为 system。
