# 研发规范与代码管理

## 代码规范

项目代码使用统一的代码风格工具（如 Prettier、ESLint、Pylint），提交前必须通过检查。
变量、函数、类命名需清晰表达用途，禁止使用无意义缩写。
关键业务逻辑必须编写单元测试，核心模块测试覆盖率不低于 80%。

## 版本管理

使用 Git 进行版本管理，分支策略采用 Git Flow：
- main：生产分支，禁止直接提交代码。
- develop：开发分支，日常开发在此合并。
- feature：功能分支，从 develop 拉出，完成后合并回 develop。
- release：发布分支，从 develop 拉出，测试通过后合并到 main。
- hotfix：紧急修复分支，从 main 拉出，修复后同时合并到 main 和 develop。

提交信息格式：`类型: 描述`，类型包括 feat（新功能）、fix（修复）、docs（文档）、refactor（重构）、test（测试）。

## 代码评审

所有代码提交到 develop/main 前必须经过代码评审（Code Review）。
评审要求：至少 1 名同组工程师评审，关键模块需技术负责人评审。
评审关注：代码质量、逻辑正确性、安全性、性能、可维护性。

## 发布流程

版本发布流程：代码冻结 → 测试验证 → 灰度发布 → 全量发布 → 线上监控。
发布窗口：周二至周四 14:00-16:00，重大版本需提前发布计划并经审批。
每次发布需记录：版本号、发布时间、变更内容、回滚方案。
发布后需在监控系统观察 30 分钟，出现异常立即执行回滚预案。

## 环境管理

环境分为：开发环境（dev）、测试环境（test）、预发布环境（staging）、生产环境（prod）。
代码部署到测试及以上环境需通过 CI 流水线自动构建和部署。
生产环境的数据库变更需 DBA 审核，禁止直接在生产环境手动修改数据。
